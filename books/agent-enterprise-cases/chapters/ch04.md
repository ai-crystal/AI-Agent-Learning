# 第 4 章 案例：研发代码维护

## 4.1 背景

虚构 SaaS 团队“北栈”有约 80 个代码仓库。日常维护包括修复小 bug、补测试、更新依赖和处理重复 issue。团队希望 Agent 承担一部分“定位、修改、跑测试、提交 PR”的工作，但不允许自动合并。

## 4.2 输入与权限

任务输入是一个 issue：

```json
{
  "issue_id": "ISSUE-431",
  "repo": "order-service",
  "title": "退款金额在折扣订单上多算 1 元",
  "reproduction": "年付订单使用首年折扣后退款",
  "labels": ["bug", "billing"],
  "allowed_paths": ["src/refund/", "tests/refund/"],
  "forbidden": [".env", "secrets/", "infra/"]
}
```

Agent 使用只读 token 拉取仓库，在隔离沙箱中写代码；它不能访问生产凭据、不能改 CI 配置、不能直接合并。提交通过 PR，由代码所有者评审。

## 4.3 一条工作轨迹

```text
1. 读 issue 和仓库结构
2. 搜索 refund、discount、rounding 相关代码
3. 跑现有退款测试，记录基线
4. 写一个复现失败案例测试
5. 修改计算逻辑
6. 跑定向测试和全量测试
7. 检查改动范围是否越界
8. 生成 PR 描述：原因、改动、测试结果、风险
9. 请求 code owner 评审
```

失败时不要假装通过。测试环境缺失、依赖下载失败或超时都应写进 PR 描述，让人判断。

## 4.4 工具和沙箱

需要的工具包括：

- `read_file`、`search_code`、`git_diff`；
- `run_tests`，限制工作目录、CPU、时间和网络；
- `open_pr`，不包含合并权限；
- `comment_issue`，需要明确仓库和 issue。

代码执行环境要禁止宿主机密钥、生产网络和任意安装。测试超时要能杀掉子进程。

## 4.5 失败模式

- 只改了测试，让测试适配错误代码；
- 修改了范围外文件；
- 通过关闭测试或跳过检查“修复”问题；
- PR 描述声称全部通过，实际只跑了部分；
- 把真实密钥写进代码或日志；
- 在多个仓库之间错误复制代码。

因此评测要检查“测试是否真实通过”“改动是否在允许范围”“是否新增敏感信息”，而不只看 diff 是否像修复。

## 4.6 验收

- 修复成功率；
- 测试通过且未降低覆盖；
- 人工评审接受率；
- 平均 PR 大小和回合数；
- 越界修改率；
- 失败 PR 的原因分布。

研发 Agent 的价值是把重复工作压缩，而不是追求自动合并。人类评审仍然是责任边界。
