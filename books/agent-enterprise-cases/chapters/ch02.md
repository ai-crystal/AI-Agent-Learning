# 第 2 章 案例：客服知识助手

## 2.1 背景

虚构公司“北辰云”提供企业协作软件，客服团队约 120 人，处理账单、退款、账号和功能咨询。知识分散在产品手册、政策库、历史工单和计费系统中。

目标不是“让 Agent 回答所有问题”，而是：

- 一线客服能更快找到当前政策；
- 常见问题给出带引用的回答；
- 涉及金额、权限和例外时转人工；
- 不把旧政策或别的租户资料混进来。

## 2.2 数据与权限

数据源：

- 产品文档：公开，按版本更新；
- 退款政策：内部，按地区/产品/日期生效；
- 工单：含客户信息，只允许当前工单参与人和主管查看；
- 计费系统：通过 API 查询，按租户隔离。

检索前必须带 `tenant_id`、用户角色、工单号和当前时间。工单内容不能进入共享缓存；文档按版本过滤，旧政策只作历史对照。

## 2.3 一条请求

用户说：

> 我们年付专业版用了三个月，有首年折扣，能退多少？

Agent 的流程：

```text
1. 从当前工单取 tenant、订单号、产品、地区；缺失则追问
2. get_order 查询支付金额、购买时间、折扣
3. search_policy 按产品/地区/日期检索当前政策
4. 重排，保留主规则、折扣例外、计算示例
5. 计算退款金额；金额为教学示例
6. 若金额超过客服权限或存在例外，转财务审批
7. 回复引用政策章节和订单事实，不承诺到账时间
```

一个合格的回答应包含：

- 用的是哪一版政策；
- 退款按什么规则计算；
- 哪些条件来自订单，哪些来自政策；
- 当前是“可申请”还是“已批准/已到账”。

## 2.4 工具设计

`get_order` 只读，返回结构化字段；`search_policy` 强制版本和地区过滤；`submit_refund` 是写操作，需要审批和幂等键。

客服 Agent 不应拥有“修改订单金额”或“删除工单”的工具。工具名单越短，注入和误用的面越小。

## 2.5 失败处理

- 检索不到当前政策：明确说资料不足，不拿旧政策补；
- 订单查不到：要求用户核对订单号，不猜；
- 金额超过权限：转人工，不拆分成多笔绕过；
- 退款服务超时：查询退款单状态，禁止直接重发；
- 文档中出现可疑指令：当数据展示，不执行。

## 2.6 验收

- 政策引用准确率；
- 退款金额计算正确率；
- 越权检索为 0；
- 需要人工的比例；
- 一次解决率；
- 平均处理时长；
- 旧政策误用率。

这些指标要在上线前有基线，并按问题类型分组，不能只看总体满意度。

## 2.7 复盘要点

客服项目最常见的失败不是模型不会回答，而是知识没有版本、工单权限没有进入检索、退款动作没有幂等。把这三件事做好，模型能力才有发挥空间。
