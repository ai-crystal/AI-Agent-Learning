# 第 5 章 案例：经营数据助手

## 5.1 背景

虚构零售企业“青禾”希望业务人员用自然语言查询销售、库存和退款指标，而不必等数据团队写 SQL。数据分散在数仓和业务系统，指标定义经常被不同团队解释成不同口径。

## 5.2 先建语义层

如果直接让模型写 SQL，模型可能：

- 选错表或字段；
- 把“销售额”理解成含税/未税、含退货/不含退货；
- 漏掉租户和时间过滤；
- 生成全表扫描或危险更新。

更稳妥的架构是：**语义层 + 受控查询**。业务指标先被定义为可执行对象：

```json
{
  "metric": "net_revenue",
  "definition": "paid_amount - refunded_amount",
  "dimensions": ["region", "channel", "month"],
  "filters": {"tenant_id": "required", "status": "paid"},
  "owner": "finance-analytics"
}
```

模型把问题映射到指标和维度，程序生成参数化查询；不确定时给出候选，不直接猜。

## 5.3 一条查询

用户问：

> 华东区上个月退款后的净销售额是多少？

Agent 解析为：

```text
metric: net_revenue
region: 华东
period: 2026-10
grain: month
```

返回结果同时显示口径、时间范围、数据更新时间和查询条件。图表只是表达，指标定义才是结论的依据。

## 5.4 权限和行级隔离

业务人员只能看自己负责的区域；财务可以看全部，但不能看与任务无关的个人数据。权限必须在 SQL 或语义层执行，而不是生成结果后删行。

多租户系统要把 `tenant_id` 放进查询模板；模型不允许自由拼接字符串。只读账号不能执行 DDL/DML。

## 5.5 失败模式

- 指标口径不一致；
- 时间边界错误（自然月/滚动 30 天）；
- 退款和取消订单重复计算；
- 图表坐标或单位误导；
- 数据延迟未标注；
- 把空结果解释成“销售为零”。

回答应明确区分“数据为 0”和“没有数据/权限不足”。

## 5.6 验收

- 指标口径一致率；
- 查询结果与标准 SQL 对比；
- 权限越界为 0；
- 业务人员采纳率；
- 平均查询时间；
- 追问/澄清率；
- 数据延迟标注完整率。

经营数据 Agent 的核心不是自然语言生成 SQL，而是把业务定义、权限和数据质量固定下来。

## 5.7 语义层片段

```text
指标 net_revenue
  表达式 paid_amount - refunded_amount
  默认过滤 status = paid
  可用维度 region, channel, month
  权限：按 tenant_id、region 过滤
```

模型只选择指标、维度和时间，不直接拼 SQL。程序用模板生成参数化查询；模型无权访问原始明细，除非任务和权限都允许。

## 5.8 结果解释

回答要附带口径、时间范围、数据更新时间和筛选条件。图表不能替代定义：同一个“销售额”可能含税或不含税，必须说明。空结果要区分“没有数据”“无权限”和“查询失败”。

## 5.9 验收

用标准 SQL 和人工作答做对照，按问题类型统计指标口径错误；权限越界为 0；数据延迟要标注。业务人员采纳率可以提高，但不能用它替代事实正确性。
