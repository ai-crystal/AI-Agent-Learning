# 第 7 章 案例：内部知识门户

## 7.1 背景

虚构集团“海岳”有多个部门知识库、Wiki、工单和对象存储。员工希望用一个入口搜索“报销政策”“部署流程”“客户案例”，但不同部门的内容权限、更新频率和格式差异很大。

## 7.2 联邦检索

不要把全部文档复制到一个共享索引。可以采用联邦检索：

```text
用户查询
→ 识别意图和部门
→ 并行查询各内容源（带用户身份）
→ 合并去重
→ 重排
→ 标注来源和更新时间
```

每个连接器返回统一的最小字段：标题、片段、来源、所有者、更新时间、权限和链接。权限在各源查询时执行，不能先把内容汇总再做过滤。

## 7.3 内容责任

知识门户最容易失效的原因是内容过期。每条知识需要有：

- 所有者；
- 最近确认时间；
- 适用范围；
- 过期策略；
- 反馈入口。

Agent 回答时应显示“最后更新”与“可能不适用”的提示。对政策、财务和人事内容，宁可转给内容所有者，也不要用过期文档硬答。

## 7.4 多 Agent 的边界

可以为不同内容源设置检索 Agent，但不应让多个 Agent 自由群聊。更可控的结构是：

- 路由器选择知识域；
- 各域检索器返回证据；
- 一个汇总器处理冲突和引用；
- 权限和引用校验由程序执行。

Agent 数量增加会带来协调成本和错误传播；只有在内容域、权限或工具确实独立时才拆分。

## 7.5 失败模式

- 搜到了无权限文档的标题或片段；
- 旧版本覆盖新版本；
- 同名政策属于不同部门；
- 链接失效；
- 搜索只覆盖部分源，却宣称“全公司”；
- 把文档中的指令当系统规则。

## 7.6 验收

- 各内容源的覆盖率；
- 权限越界为 0；
- 过期内容误用率；
- 引用可点击率；
- 内容所有者反馈闭环；
- 用户找到答案的时间；
- 无法回答时的转交率。

知识门户的价值是让人找到“谁负责、哪一版、是否适用”，而不只是给出一段看似完整的总结。

## 7.7 连接器清单

| 源 | 字段 | 权限单位 | 更新 |
| --- | --- | --- | --- |
| Wiki | 标题、正文、链接 | 部门/空间 | 每日 |
| 工单 | 问题、解决记录 | 工单参与人 | 实时 |
| 对象存储 | 文档、版本 | 文件 ACL | 上传时 |
| HR 政策 | 政策、生效日 | 全员/地区 | 版本更新 |

连接器要返回统一的权限和版本字段，不能把不同系统的访问控制混成一个布尔值。

## 7.8 过期与反馈

每条结果显示最后确认时间。用户点“这不对”时，反馈进入内容所有者队列，而不是只用于调整排序。没有人维护的内容，最终会污染所有回答。

## 7.9 多 Agent 的停止条件

如果多个检索器已经能覆盖内容域，不要再增加一个“协调 Agent”。只有在任务确实需要不同工具、不同权限或不同验证方式时才拆分，并限制轮数和预算。
