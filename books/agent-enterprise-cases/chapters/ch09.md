# 第 9 章 失败、退出与治理

## 9.1 项目为什么会失败

常见原因：

- 选了一个无法验收的宽泛目标；
- 数据权限没有提前解决；
- 把人工流程当成 Agent 可以自由替代；
- 没有评测，只靠演示判断；
- 工具没有幂等，重试造成重复副作用；
- 成本随使用量增长，但没有预算；
- 业务方不定义责任人，出问题无人处理。

这些问题通常在项目开始时就存在，只是上线后才暴露。

## 9.2 退出条件

项目应该在开始前写清停止条件，例如：

- 影子运行解决率低于人工基线；
- 关键数据无法取得合法授权；
- 高风险动作无法做到审批和回滚；
- 单位任务成本超过业务可接受上限；
- 安全评审无法通过。

达不到条件就停止或缩小范围，不是继续加模型。

## 9.3 成本治理

成本要按任务、租户和功能拆开。一个功能可能“技术上可行”，但每次调用成本高于人工；另一种情况是低频高价值任务成本高但可接受。没有统一答案，需要业务定价。

当预算接近上限时，系统应降级、转人工或延后，而不是悄悄继续烧钱。

## 9.4 组织责任

Agent 项目需要明确：

- 业务所有者：定义目标和验收；
- 数据所有者：授权和更新数据；
- 安全/合规：审核权限和外泄风险；
- 工程团队：运行、观测和回滚；
- 一线用户：反馈和接管。

只有工程团队负责，项目很难进入真实流程；只有业务方推动，系统又容易缺少运行保障。

## 9.5 退役

Agent 也可能被替换或停用。退役时要：

- 停止新任务；
- 处理未完成任务；
- 导出审计记录；
- 回收凭据和权限；
- 删除或归档敏感数据；
- 通知用户替代流程。

没有退役方案的系统，会在组织变化后变成无人维护的风险。

## 9.6 本章的结论

企业 Agent 的成败不只在模型，而在目标、数据、权限、验收和组织责任。敢于设定退出条件，是项目治理的一部分，不是失败。

## 9.6 成本退出线

为每个功能设单位成本上限：每次建议、每次自动执行、每个成功任务。若成本长期高于人工成本，应该缩小范围、换更便宜模型、增加缓存，或者停止。不要用“未来模型会降价”作为当前预算假设。

## 9.7 供应商退出

避免把业务规则、提示和评测全部绑定在一个供应商的私有格式里。保留可导出的数据、工具接口和评测集；更换模型或平台时，至少能重跑同一批任务。

## 9.8 复盘模板

```text
影响：哪些用户/租户/任务
时间线：发现、止血、恢复
根因：数据/工具/模型/权限/流程
证据：trace、请求 ID、外部状态
修复：代码/规则/权限/流程
回归：新增哪个评测用例
责任：谁批准、谁跟进
```

复盘的目标是改变系统，而不是找一个人背锅。
