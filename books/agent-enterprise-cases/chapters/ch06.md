# 第 6 章 案例：跨系统流程自动化

## 6.1 背景

虚构企业“云桥”的报价到收款流程跨 CRM、合同、ERP 和财务系统。销售确认订单后，需要创建合同、检查信用额度、生成发货单、开票并通知财务。每一步都有审批和失败可能。

Agent 的目标不是“一键完成所有事”，而是把流程推进到下一个需要人判断的节点。

## 6.2 流程状态

```text
draft
→ contract_created
→ credit_checking
→ credit_approved / credit_rejected
→ shipment_created
→ invoice_issued
→ closed
```

每个状态都要有外部系统 ID。例如合同 ID、ERP 订单号、发票号。恢复时按这些 ID 查询，而不是重新创建。

## 6.3 幂等和补偿

创建合同、发货单、发票都是写操作。请求要带：

```json
{
  "workflow_id": "wf-2026-017",
  "step": "create_invoice",
  "idempotency_key": "wf-2026-017-invoice-1",
  "external_ref": "erp-order-8831"
}
```

如果发票服务超时，先按幂等键查询是否已创建；确认未创建才重试。若已经创建但通知失败，只补通知，不重复开票。

不可逆动作需要补偿方案：已发货但合同审批撤销，需要拦截或人工处理，不能假装回滚。

## 6.4 审批

信用额度不足、折扣超限、客户信息变更等节点必须停下等审批。审批界面要展示：

- 客户、订单、金额、折扣；
- 触发审批的规则；
- 当前流程状态和已执行动作；
- 拒绝/通过的后果。

审批不是“是否允许 Agent”，而是“是否允许这笔业务”。

## 6.5 长任务

流程可能持续数小时或数天。运行时要把等待外部系统、等待审批、失败重试分开，不能让一个 worker 一直占用。状态存检查点，事件写 trace；用户能看到当前卡在哪一步。

## 6.6 失败模式

- 重复创建合同/发票；
- 状态显示完成，外部系统实际失败；
- 审批通过后继续使用旧报价；
- 跨系统字段映射错误；
- 取消流程没有补偿；
- 通知发给了错误的客户联系人。

## 6.7 验收

- 流程一次通过率；
- 重复创建为 0；
- 人工审批时长；
- 失败恢复成功率；
- 外部系统状态一致率；
- 每个节点的责任人和审计记录。

跨系统自动化的难点是状态一致性和副作用，而不是让模型写一段流程说明。
