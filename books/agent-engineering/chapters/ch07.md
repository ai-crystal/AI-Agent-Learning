# 第 7 章 评测与回归

## 7.1 三层评测

Agent 评测至少有三个层次：

| 层 | 问题 | 例子 |
| --- | --- | --- |
| 单元 | 一个工具/模型调用是否正确 | schema 校验、参数解析 |
| 轨迹 | 一次任务是否完成且过程合规 | 工具顺序、权限、步数 |
| 系统 | 一类任务是否稳定、可接受 | 解决率、延迟、成本、回退率 |

只看最终答案，会把工具越权、重复执行和不可接受的中间步骤都隐藏掉。一个请求可能“答对了”，但绕过了审批。

## 7.2 评测用例

```json
{
  "case_id": "refund-017",
  "task": "为订单 A1023 提交符合条件的退款",
  "tenant": "t-42",
  "user": "u-108",
  "expected": {
    "outcome": "refund_submitted",
    "must_call": ["get_order", "search_policy", "submit_refund"],
    "must_not": ["refund_other_tenant", "skip_approval"],
    "max_steps": 12,
    "max_usd": 0.40
  }
}
```

评测不只是检查文本答案，还要检查工具调用、权限、预算和副作用。

## 7.3 测试集分布

一个可用的测试集要覆盖：

- 常见成功路径；
- 缺少实体、需要追问；
- 工具超时/部分失败；
- 无权限资源；
- 政策过期或冲突；
- 无答案；
- 提示注入；
- 接近预算上限的长任务。

如果测试集只包含“顺利完成任务”，系统会奖励那些跳过校验、直接执行的策略。

## 7.4 回归和版本

每次修改提示、模型、工具、权限或上下文策略，都要跑固定回归集，并记录：

- 成功/失败变化；
- 新增失败类型；
- 工具调用次数；
- P50/P95 延迟；
- 平均/峰值成本；
- 人工接管率。

不要只看总分。一个版本可能把简单任务做得更快，却让高风险任务更容易越权。

## 7.5 线上评测

线上无法像离线一样知道标准答案，但可以收集：

- 用户是否采纳；
- 是否转人工；
- 是否触发重试；
- 是否被回滚；
- 工具失败和权限拒绝；
- 人工抽检。

线上指标用于发现分布变化，不能替代有标注的离线集。用户点击“满意”不等于答案事实正确，业务完成状态通常更可靠。

## 7.6 评测的陷阱

**用模型给自己打分。** 模型会偏好自己的表达和盲区；需要规则、人工和不同模型交叉。

**只看平均。** 高风险类别需要单独统计。

**测试集污染。** 测试用例进入提示示例或训练数据，分数会虚高。

**忽略成本。** 准确率略高但成本翻倍的系统未必值得上线。

## 7.7 本章的结论

评测要定位责任层：工具错、权限错、上下文错还是模型错。固定任务集、结构化轨迹、失败分类和版本记录，比一次“看起来不错”的演示更有价值。

下一章讨论当这些评测暴露出超时、重复和级联失败时，运行时怎样兜底。

## 7.8 一个回归门槛

发布前可以设置硬门槛：

- 高风险用例越权数为 0；
- 退款金额计算全部正确；
- 工具重复副作用为 0；
- 无答案用例的拒答率不低于基线；
- P95 延迟和成本不超过预算。

门槛不通过就不发布。不要用“平均分提高了”抵消一个高风险类别的退化。

## 7.9 评测数据治理

评测集会包含真实业务数据，必须有访问控制和脱敏。用例的期望结果需要版本；业务规则改变后，旧期望要更新并记录原因，否则回归结果会指向错误方向。
