# 第 5 章 上下文、检查点与状态管理

## 5.1 上下文是运行资源

上下文窗口、状态存储和检查点经常被混为一谈。它们解决的问题不同：

- **上下文窗口**：这一次模型调用能看到什么；
- **状态存储**：系统为了继续任务需要记住什么；
- **检查点**：在某个时刻保存的可恢复快照。

把所有状态都放进上下文，会挤占证据和输出空间；把所有上下文都当状态，会把临时文本误当成不可变事实。

## 5.2 预算表

一次调用应明确分配：

| 部分 | 示例预算 | 处理方式 |
| --- | ---: | --- |
| 系统规则 | 700 token | 固定、版本化 |
| 任务与已确认事实 | 600 token | 结构化状态 |
| 工具结果/证据 | 3,000 token | 去重、截断 |
| 最近对话 | 1,200 token | 滑动窗口 |
| 输出预留 | 1,500 token | 不挤占 |
| 安全余量 | 1,000 token | 估算误差 |

预算不是一次设定永远不变。不同任务可以调整，但必须有总数和超限策略：先删低价值历史，还是先截断工具结果，还是要求模型缩小查询。

## 5.3 摘要与原文

摘要可以节省上下文，但不能替代原文。一个可维护的做法是保存三层：

1. 原始事件与工具结果（不可变日志）；
2. 可回查的结构化记录（任务、证据 ID、外部 ID）；
3. 当前上下文里的摘要（可重建）。

摘要必须标注事实来源。如果摘要说“订单已核对”，应能回到哪次工具调用、哪个订单号和哪个时间。否则恢复时无法判断摘要是否过期。

## 5.4 检查点内容

```json
{
  "task_id": "task-017",
  "status": "waiting_human",
  "state_version": 4,
  "confirmed": {"order_id": "A1023", "amount": 199.0},
  "plan": ["查订单", "查政策", "计算", "提交退款"],
  "cursor": 3,
  "idempotency": {"refund": "task-017-refund-1"},
  "evidence": ["E1", "E2"],
  "budget_used": {"steps": 6, "usd": 0.12},
  "model": "model-x@2026-10",
  "prompt": "agent-runner@v3",
  "updated_at": "2026-11-17T10:21:04Z"
}
```

`state_version` 用于乐观锁：两个 worker 同时恢复同一任务时，只有一个能成功推进，另一个应重新读取状态。

## 5.5 上下文污染

长时间运行后，上下文会积累：

- 过期政策；
- 失败工具的重复错误；
- 已经排除的方案；
- 用户临时的猜测；
- 无关的搜索结果。

清理时要区分“可以删除的临时文本”和“必须保留的事实”。失败的工具调用可以摘要为“已失败，原因是 X，不要重复”，而不是保留完整错误栈；过期的证据应标记版本，不要和新证据混在一起。

## 5.6 失败模式

**摘要覆盖原文。** 摘要写错后无法回查；必须保留原始日志和证据 ID。

**上下文无限增长。** 每步都追加全部历史，成本和干扰持续上升。

**检查点包含密钥。** 检查点会持久化，必须脱敏并设置访问控制。

**恢复没有版本。** 模型、提示或工具升级后，旧检查点可能不能直接复用；要记录版本并允许兼容/迁移。

## 5.7 本章的结论

上下文是这次调用的工作台，状态是任务跨调用的骨架，检查点是恢复所需的快照。三者要分层，不要互相替代。

一个好的状态系统应让任务在模型超时、进程重启或人工等待后继续，而不是从头猜起。下一章会让这些状态变得可观察：trace、指标和回放。
