# 第 9 章 成本、容量与部署

## 9.1 成本结构

一次 Agent 请求可能消耗：

- 模型输入/输出 token；
- 工具 API 调用；
- 向量/关键词检索；
- 重排模型；
- 代码沙箱 CPU/内存；
- 日志、trace 和存储。

成本要按任务、租户、工具和模型分别统计。只看月度总账单，无法知道是哪个功能在烧钱。

## 9.2 预算

预算至少有三层：

```text
单任务：最多 20 步、0.40 美元
单用户/租户：每天 5 美元
系统：每月固定上限
```

达到上限时，系统应降级、转人工或停止，而不是继续消耗。预算检查要在调用前和调用后都做，避免单次调用超支。

## 9.3 缓存与模型路由

可以缓存：

- 相同文档的解析/embedding；
- 相同查询的检索结果；
- 相同参数的只读工具结果；
- 重复问题的最终答案（低风险、短时效）。

模型路由则按任务选择便宜或强的模型：格式整理、分类和抽取用小模型；复杂规划、代码修复和高风险判断用更强模型。路由规则要可评测，不能只凭感觉。

## 9.4 容量

并发不是越大越好。模型和工具都有速率限制，超过后会排队、超时或返回 429。需要：

- 队列和优先级；
- 每租户限流；
- 超时和取消；
- 峰值保护；
- 人工任务单独队列。

长任务不要占用短请求的 worker；否则一个批处理任务会让所有在线用户变慢。

## 9.5 环境与发布

至少区分开发、预发和生产。每个环境有自己的凭据、索引和预算。发布时：

1. 构建不可变版本；
2. 跑固定评测集；
3. 小流量灰度；
4. 观察失败分类、延迟和成本；
5. 可一键回滚。

提示、工具 schema、模型和索引都应该有版本。只回滚代码，不回滚提示或索引，故障可能继续存在。

## 9.6 本章的结论

成本、容量和部署是同一个问题的三个面：系统能否在可控资源下稳定服务。预算要细，缓存要可失效，路由要可评测，发布要可灰度、可回滚。
