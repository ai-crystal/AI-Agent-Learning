# 第 1 章 从演示到生产

## 1.1 演示系统缺少什么

一个演示 Agent 通常只证明三件事：模型能理解任务、工具能被调用、结果能被拼成回答。生产系统还要回答更多问题：

- 请求来自哪个租户、哪个用户，他能看什么？
- 工具失败、模型超时或返回格式错误时怎么办？
- 一次任务持续几十分钟，中断后怎样恢复？
- 多少钱、多少并发、多少延迟是可以接受的？
- 出错时怎样证明系统做了什么，怎样阻止同类错误再次发生？

演示看的是“成功路径”，生产看的是“失败路径”。两者不是同一张系统图。

## 1.2 一次生产事故

假设客服 Agent 的任务是：

> 帮用户查订单 A1023，如果符合政策就发起退款。

演示版本可以调用 `get_order`、`search_policy` 和 `refund`。生产版本在真实请求中可能出现：

```text
1. get_order 成功，但返回了另一个租户的订单；
2. 政策检索到了旧版本；
3. refund 超时，系统重试，生成两笔退款；
4. 模型在最终回答中承诺“已退款”，实际只是“已提交”；
5. 日志只记录了模型输出，没有记录工具参数和外部请求 ID。
```

每一个问题都不是“模型不够聪明”能解释的。它们分别属于权限、数据版本、幂等、状态表达和可观测性。

## 1.3 生产系统的五个层

可以用五层理解 Agent 工程：

| 层 | 关注点 | 典型问题 |
| --- | --- | --- |
| 交互层 | 用户、渠道、输入输出 | 输入不可信、输出格式错误 |
| 决策层 | 模型、提示、上下文 | 误判、幻觉、上下文污染 |
| 工具层 | 函数、API、代码、浏览器 | 参数错误、超时、重复执行 |
| 状态层 | 会话、计划、检查点 | 中断丢失、恢复重做 |
| 运行层 | 权限、预算、观测、发布 | 越权、成本失控、无法回滚 |

模型只占其中一层。把所有责任都推给模型，通常意味着其他层没有被设计。

## 1.4 一个最小生产任务

以“查订单并发起退款”为例，一个相对完整的请求流程可以写成：

```text
request_id: req-2026-1117-0042
tenant_id: t-42
user_id: u-108
intent: refund_request
entities: {order_id: "A1023"}
policy_version: 2026-07-01

1. 鉴权：确认 u-108 能看到 A1023
2. 读取订单：返回金额 199.00、状态 paid、购买时间
3. 检索政策：按产品/地区/日期过滤，取当前版本
4. 决策：金额、时间、折扣条件是否满足
5. 预演：显示将退金额和账户
6. 审批：按金额/风险进入人工或自动
7. 执行：带 idempotency_key 调用 refund
8. 校验：查询退款状态，区分 pending/completed/failed
9. 回复：引用政策、说明状态，不把 pending 说成 completed
10. 记录：保存 trace、工具结果和外部请求 ID
```

这条链路中，模型可以负责理解请求、组织证据和生成解释，但不能单独决定“跳过鉴权”或“把 pending 当成功”。程序必须拥有不可绕过的边界。

## 1.5 原型转生产的检查顺序

推荐的顺序不是先优化模型，而是：

1. 先定义任务的成功、失败和不可接受结果；
2. 再划清数据、工具和权限边界；
3. 然后建立 trace 和可重复的评测；
4. 最后才是提示、模型和成本调优。

如果系统无法说明“这次请求为什么被允许执行”，换模型不会解决安全问题；如果系统无法复现一条失败轨迹，换模型也无法证明问题被修复。

## 1.6 本章的结论

生产 Agent 是一个受约束的执行系统，不是一段更长的提示。它的核心问题是：**谁在什么权限下，能对什么资源，执行什么动作，留下什么证据，失败后怎样恢复。**

后续章节会围绕这条主线展开：运行时负责推进，工具负责执行，权限负责限制，状态负责恢复，观测负责解释，评测负责证明，可靠性负责兜底。
