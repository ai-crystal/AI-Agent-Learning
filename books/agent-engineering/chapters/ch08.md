# 第 8 章 可靠性：超时、重试与降级

## 8.1 失败是常态

生产 Agent 会同时面对模型、网络、工具和外部系统的失败。可靠性设计的目标不是“永远不出错”，而是出错时系统仍然可控：不重复副作用、不无限等待、不让一个坏工具拖垮全部任务。

## 8.2 超时

不同动作需要不同超时：

```text
模型调用     30—120 秒（取决于任务）
普通查询     5—15 秒
文件读取     10—30 秒
编译/测试    几分钟
人工审批     小时/天，不能按秒超时
```

超时后要确认子进程或请求是否真的停止。只停止等待、不取消底层任务，会留下后台进程和重复执行风险。

## 8.3 重试

重试要区分错误：

- 网络抖动、503、限流：可以退避重试；
- 参数错误、权限拒绝：不要重试；
- 不确定是否成功的写操作：先查询状态，不能直接重发；
- 模型格式错误：有限次数修复，超过后停止。

重试次数和总时限都要有上限。指数退避加随机抖动可以避免大量任务同时重试。

## 8.4 幂等和对账

写操作必须先有幂等键，再谈重试。响应丢失时，恢复流程先按幂等键或业务 ID 查询外部系统，确认是否已经执行，再决定补偿还是继续。

对账任务可以定期扫描“本地状态是 pending、外部状态是 completed”的记录，修正不一致。不要只相信 Agent 自己说“已经完成”。

## 8.5 熔断和降级

如果一个工具在短时间内大量失败，继续调用只会扩大故障。可以：

- 暂时熔断该工具；
- 返回缓存/上一次结果（明确标注时效）；
- 切换到备用模型或人工队列；
- 将任务标记为“稍后重试”。

降级必须让用户知道。把降级结果伪装成正常结果，比直接报错更危险。

## 8.6 级联失败

一个 Agent 可能同时依赖搜索、数据库、邮件和支付。某个下游变慢后，主循环不断重试，上下文越来越大，最后成本和时间一起爆掉。

需要全局预算和断路器：当任务超过最大步数、最大时长或最大金额，停止并发起人工接管。不要让单个工具的故障把整个队列拖死。

## 8.7 本章的结论

可靠性的核心是：**能停、能查、能重试、能恢复、能降级**。超时和重试必须配合幂等与对账；降级必须透明；系统必须有总预算和人工接管路径。

## 8.8 故障注入

在预发环境主动注入：模型超时、工具 503、响应丢失、重复回调、磁盘满和权限拒绝。观察系统是否正确停止、重试、对账和转人工。故障注入不是破坏测试，而是验证“失败路径也被实现”。

## 8.9 队列与背压

当请求超过处理能力时，系统应排队或拒绝，而不是无限创建 worker。队列要有优先级、最大长度、单租户配额和超时；长任务与短请求分开，避免批处理拖慢在线服务。
