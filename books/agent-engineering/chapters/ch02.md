# 第 2 章 运行时、状态与恢复

## 2.1 主循环不是全部

一个最简单的 Agent 循环是：

```text
while not done:
    response = model(context)
    action = parse(response)
    observation = execute(action)
    context += observation
```

它能跑通演示，但没有回答“任务是什么状态”“做到哪一步”“中断后怎么办”。生产运行时需要显式的任务状态，而不是只依赖一段不断增长的对话历史。

## 2.2 一个可恢复的状态

可以用下面的记录描述一次任务：

```json
{
  "task_id": "task-017",
  "status": "waiting_approval",
  "step": 6,
  "plan": ["核对订单", "检索政策", "计算金额", "发起退款"],
  "completed": ["核对订单", "检索政策", "计算金额"],
  "pending": ["发起退款"],
  "context_ref": "s3://traces/task-017/context.json",
  "approval_id": "apr-2291",
  "budget": {"max_steps": 20, "max_usd": 0.40, "used_usd": 0.12},
  "updated_at": "2026-11-17T10:21:04Z"
}
```

状态必须能回答：

- 当前正在等什么：模型、工具、审批、用户补充信息？
- 已经完成了哪些不可逆动作？
- 下一步允许调用什么工具？
- 预算是多少，已经用了多少？
- 如果恢复，是否需要重新执行某个工具？

对话历史可以很长，但任务状态应当短、结构化、可校验。

## 2.3 检查点与恢复

检查点不是“保存聊天记录”，而是保存继续执行所需的最小状态：

- 任务目标和已确认实体；
- 计划与完成进度；
- 已执行工具及其幂等键；
- 外部系统 ID（订单、工单、退款单）；
- 当前等待的审批或用户输入；
- 模型/提示/工具版本。

恢复时先读取检查点，再检查外部世界是否已经改变。比如状态说“准备发起退款”，但退款服务里已经有一笔相同 `idempotency_key` 的记录，就不能再创建第二笔。

```text
resume(task):
    state = load_checkpoint(task)
    if state.status == "waiting_approval":
        return wait_for_approval(state.approval_id)
    if state.status == "tool_inflight":
        return reconcile_tool_result(state.tool_call_id)
    return continue_loop(state)
```

`reconcile_tool_result` 是生产系统特有的步骤：中断可能发生在请求已经发出、响应尚未写回之间。恢复时不能假设“没收到结果就等于没执行”。

## 2.4 事件与状态机

把运行过程记录成事件，比只存最终状态更容易回放：

```json
{"event": "task_started", "task_id": "task-017", "at": "10:19:02"}
{"event": "tool_requested", "tool": "get_order", "args": {"order_id": "A1023"}}
{"event": "tool_completed", "tool": "get_order", "status": "ok", "latency_ms": 184}
{"event": "approval_requested", "approval_id": "apr-2291"}
{"event": "refund_submitted", "idempotency_key": "task-017-refund-1"}
```

事件流可以驱动状态机，也可以用于回放、审计和评测。它要包含时间、主体、动作、结果和外部 ID；只记录模型的自然语言解释不够。

## 2.5 并发与租户

同一个进程可能同时处理多个任务。状态不能放在全局变量里，否则任务 A 的上下文会污染任务 B。每个任务至少要有独立的：

- 会话/任务 ID；
- 上下文快照；
- 预算计数；
- 工具调用记录；
- 租户与权限范围；
- 中间文件目录。

临时文件也要按任务隔离。两个任务同时写同一个 `output.txt`，恢复时无法判断文件属于谁。

## 2.6 取消与超时

用户取消、预算耗尽或审批拒绝时，运行时应该：

1. 停止发起新的工具调用；
2. 等待已经发出的请求返回，或调用取消接口；
3. 记录哪些动作已经完成；
4. 把任务标记为 `cancelled` 或 `failed`；
5. 对不可逆动作执行补偿或人工核对。

“停止循环”不等于“停止世界”。已经提交给外部系统的操作仍然可能继续执行。

## 2.7 失败模式

**把历史当状态。** 从一段很长的对话里推断任务进度，模型可能忘记或误解；结构化状态更可靠。

**恢复时重新执行。** 没有幂等键，恢复可能造成重复退款、重复发信。

**没有等待态。** 审批和用户补充信息被当成普通模型调用，超时后任务直接失败。

**并发串状态。** 全局上下文或全局临时文件让两个任务互相污染。

## 2.8 本章的结论

生产运行时需要三样东西：推进循环、维护状态、支持恢复。状态应当结构化、可校验、可追踪；恢复必须先核对已经发生的外部副作用，而不是简单重放。
