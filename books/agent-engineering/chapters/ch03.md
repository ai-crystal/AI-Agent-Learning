# 第 3 章 工具契约与错误设计

## 3.1 工具不是函数名

模型选择一个工具时，看到的通常只有名称、说明和参数 schema。名称含糊、说明不清、参数类型不一致，会让模型“看起来会调”，实际经常传错。

一个可用的工具契约至少要写清：

- 它解决什么问题；
- 什么时候应该调用，什么时候不应该；
- 参数的类型、范围、必填项和默认值；
- 返回值结构；
- 可能的错误类型；
- 超时、幂等和权限要求。

## 3.2 一个坏工具

```json
{
  "name": "do_refund",
  "description": "退款",
  "parameters": {
    "type": "object",
    "properties": {
      "data": {"type": "string"}
    }
  }
}
```

问题很多：`data` 是订单号、金额还是整条 JSON？是否支持部分退款？“退款”是执行还是申请？失败时返回什么？模型只能猜。

## 3.3 一个较完整的工具

```json
{
  "name": "submit_refund",
  "description": "为已支付订单提交退款申请。此操作只提交，不保证即时到账；调用前必须确认订单归属和退款政策。",
  "parameters": {
    "type": "object",
    "properties": {
      "order_id": {"type": "string", "pattern": "^[A-Z][0-9]{4}$"},
      "amount": {"type": "number", "minimum": 0.01},
      "currency": {"type": "string", "enum": ["CNY", "USD"]},
      "reason_code": {"type": "string", "enum": ["duplicate", "service_issue", "policy"]}
    },
    "required": ["order_id", "amount", "currency", "reason_code"],
    "additionalProperties": false
  }
}
```

这里最重要的不是字段多少，而是动作边界：`submit_refund` 明确是“提交”，不是“已完成”；金额和币种必须结构化；原因必须来自枚举。模型仍然可能填错，但程序可以在调用前拦截。

## 3.4 参数校验

收到工具调用后，先校验再执行：

```python
def validate_refund(args, user):
    if not ORDER_RE.match(args["order_id"]):
        return error("order_id_format")
    if args["amount"] <= 0:
        return error("amount_must_positive")
    if args["currency"] not in ("CNY", "USD"):
        return error("unsupported_currency")
    if not can_view_order(user, args["order_id"]):
        return error("permission_denied")
    return ok()
```

校验失败时，不要用异常栈把整段内部信息丢给模型；返回稳定的错误码、可读原因和可修正的字段。模型需要的是“怎么改”，而不是服务器堆栈。

## 3.5 幂等

网络超时并不意味着操作没有发生。`submit_refund` 需要幂等键：

```json
{
  "idempotency_key": "task-017-refund-1",
  "order_id": "A1023",
  "amount": 199.0
}
```

相同的键重复提交，服务端应返回第一次的结果，而不是再创建一笔退款。幂等键应由程序生成并持久化；不要交给模型临时编造。

## 3.6 错误分类

工具错误至少分成：

| 类型 | 例子 | 模型应该做什么 |
| --- | --- | --- |
| 参数错误 | 订单号格式不对 | 修正参数 |
| 权限错误 | 当前用户不能看订单 | 停止并说明 |
| 暂时错误 | 503、超时 | 重试或稍后 |
| 永久错误 | 订单不存在 | 不再重试 |
| 部分成功 | 批量操作部分失败 | 报告已成功部分 |
| 结果被截断 | 输出超过上限 | 缩小查询或读取文件 |

把所有错误都变成 `"error"`，模型无法选择正确恢复动作；把所有错误都重试，可能造成重复副作用。

## 3.7 返回值要适合模型阅读

工具返回的文本会进入上下文。一个 5MB 的 JSON 会挤掉任务状态；一个只有 `{"ok":true}` 的结果又缺少模型判断所需的信息。

推荐返回紧凑的结构化结果：

```json
{
  "ok": true,
  "order_id": "A1023",
  "status": "paid",
  "amount": 199.0,
  "currency": "CNY",
  "paid_at": "2026-08-12",
  "items": 2
}
```

大结果写入文件或对象存储，只把摘要、路径和取回方式放进上下文。截断时要明确写出“已截断”和总量。

## 3.8 本章的结论

工具契约是模型和真实世界之间的协议。名称、说明、schema、错误和幂等共同决定模型能否安全使用它。

工具层要尽量让错误可分类、结果可阅读、重复可识别、权限可检查。模型可以决定“想做什么”，但不能决定“跳过校验直接执行”。

## 3.9 工具测试

工具契约需要独立测试，而不是只通过 Agent 端到端碰运气：

- 参数缺失、类型错误、超范围；
- 空结果、部分结果、超时、权限拒绝；
- 同一幂等键重复调用；
- 返回内容过长时的截断；
- 外部服务返回 HTML 错误页而不是 JSON。

测试用例可以直接调用工具层，不经过模型。工具层稳定后，Agent 的错误才更容易归因到决策层。

## 3.10 版本兼容

工具参数和返回值会演进。新增字段通常兼容，删除字段或改变含义会破坏旧提示和旧检查点。每次不兼容变更都要提高工具版本，更新 schema、测试和 Agent 提示；旧任务恢复时应使用它当时记录的工具版本，或者明确迁移。
