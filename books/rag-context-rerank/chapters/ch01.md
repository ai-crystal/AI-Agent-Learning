# 第 1 章 RAG 的问题边界

## 1.1 三种知识位置

讨论 RAG 之前，先区分知识可能在哪里。

**参数记忆**。模型在预训练和后续对齐中把大量模式压进权重。它擅长语言、常识和常见概念，但你无法像更新数据库一样精确删除一条事实，也无法保证某条知识在需要时一定被召回。

**上下文记忆**。这次请求里放进去的文本、图片、工具结果和历史。它立刻生效，不需要训练，但受窗口、成本和注意力分配限制；请求结束后通常不会自动留存。

**外部知识库**。文档、数据库、工单、网页、代码仓库和业务 API。它可以被精确定位、更新和授权，但系统必须先把它们解析成模型能使用的片段。

RAG 的核心动作，是在生成前从第三种位置找到证据，放进第二种位置，弥补第一种位置的缺口。它并不是“让模型记住更多”，而是“让这次回答有可查的来源”。

## 1.2 什么时候需要 RAG

可以把问题拆成四个判断。

**知识是否经常变化。** 退款政策、商品价格、库存、内部流程、项目文档会变化。把这些内容训练进参数既昂贵又无法保证时效，检索更合适。

**是否需要出处。** 如果用户或审计者要看到“这句话来自哪份文件哪一节”，仅靠参数记忆无法提供可靠引用。RAG 可以保留文档 ID、版本、页码和片段定位。

**是否属于长尾知识。** 某个客户内部的命名、某个仓库的特殊约定、某份合同的附件，通常不在通用语料里。它们适合按需检索，而不是期待模型碰巧见过。

**是否有权限边界。** 不同用户能看的文档不同。把全部知识塞进一个共享索引，回答时再靠提示词要求“不要泄露”，并不能替代检索前的权限过滤。

反过来，有些任务不适合优先做 RAG：

- 知识很小且稳定，直接写在系统提示里更简单；
- 需要对整本书做统一的结构性推理，而不是找几个片段；
- 延迟预算极低，连一次额外检索和重排都无法容纳；
- 文档质量极差，解析和清洗的成本高于收益。

这时应该先做数据治理、缓存或规则系统，而不是把问题包装成“上 RAG”。

## 1.3 一个教学请求

假设一个 SaaS 产品有以下资料：

- `policy-refund-2026.pdf`：退款政策，含地区差异；
- `pricing-2026.md`：套餐与计费周期；
- `tickets/`：客服工单，含未公开的客户信息；
- `release-notes.md`：版本变更。

用户问：

> 我买的是年付套餐，三个月后想退款，还能退多少？

一个没有检索的回答可能给出泛泛的“按比例退款”，听起来合理，却可能忽略了地区、促销条款和已使用服务。一个有检索但没有重排的系统，可能同时找到“月付退款”“年付退款”和“企业合同退款”三块内容，把互相矛盾的片段一起塞给模型。

教学上可以把链路写成下面的记录（公司、政策数字均为虚构）：

```text
query: 年付套餐使用三个月后退款金额
filters: product=pro, region=CN
candidates:
  c01 月付退款：剩余整月可退              score=0.81
  c02 年付退款：按未使用月份比例计算      score=0.79
  c03 促销年付：退款需扣除已用折扣        score=0.76
  c04 企业合同：按合同条款另行处理        score=0.74
rerank_top3:
  c03 促销年付条款（与用户订单类型一致）
  c02 年付退款计算规则
  c01 月付规则（作为反例，不应直接套用）
```

这里最重要的不是某个分数，而是**过滤条件和证据之间的关系**。如果订单元数据没有“促销年付”这个标签，检索器只能凭文本相似度猜；重排器也可能把“年付”误判成通用规则。RAG 的准确性从数据建模开始，而不是从模型开始。

## 1.4 RAG 与微调的分工

RAG 和微调都常被拿来解决“模型不知道”的问题，但它们改变的东西不同。

| 目标 | 更适合 RAG | 更适合微调 |
| --- | --- | --- |
| 增加可更新的知识 | 是 | 通常不是 |
| 改变回答格式和风格 | 不一定 | 是 |
| 让模型学会使用某类工具 | 可以示范 | 可以训练 |
| 提供可审计出处 | 是 | 不能保证 |
| 处理权限和租户隔离 | 检索层负责 | 训练后仍难隔离 |

两者可以组合：微调让模型更会遵守引用格式、拒答和工具调用协议；RAG 在运行时提供最新证据。不要用微调去记一份每周变化的价目表，也不要把“必须按固定 JSON 输出”完全寄托在一段很长的检索提示上。

## 1.5 成本不只是一张向量库账单

一个 RAG 请求的成本至少包括：

- 解析和清洗文档的离线计算；
- 生成 embedding 的 token 或图片费用；
- 向量索引的存储、内存和查询；
- 关键词检索、过滤和网络往返；
- 重排序模型的调用或本地推理；
- 放进上下文的证据 token；
- 生成答案的输出 token；
- 评测、日志和人工抽检。

以教学参数为例：召回 50 个片段、每个 300 token，如果全部送进重排器，输入约 15,000 token；重排后再把 8 个片段放进生成上下文，可能只有 2,400 token。**重排的价值之一，就是避免把大量候选都塞进最终提示。** 但重排本身也要花钱，所以候选数量和模型大小要一起测。

## 1.6 本章的结论

RAG 解决的是“这次回答需要外部证据”的问题。它适合变化快、需要出处、长尾或受权限控制的知识；不适合把所有问题都自动变成检索问题。

一个 RAG 系统至少有四层责任：

1. 资料能不能被正确解析和更新；
2. 查询能不能找到正确候选；
3. 候选能不能被准确排序和压缩；
4. 生成结果能不能被证据和评测支持。

后面九章会沿着这条责任链逐层拆开。先记住一句话：**检索到相似文本，不等于找到了答案依据；把文本放进上下文，也不等于模型会正确使用它。**
