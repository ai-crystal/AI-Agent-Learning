# 第 2 章 一条完整的 RAG 链路

## 2.1 从离线到在线

RAG 可以分成两条时间线。

**离线索引**处理“资料怎样变成可检索的结构”：

```text
原始文档
  → 解析（PDF/HTML/表格/OCR）
  → 清洗（去导航、修复编码、保留标题）
  → 切块（chunk）
  → 元数据（来源、版本、权限、页码）
  → embedding
  → 向量索引 + 关键词索引
```

**在线请求**处理“这次问题怎样得到答案”：

```text
用户问题 + 会话状态
  → 查询规范化/改写
  → 并行召回（向量、BM25、过滤）
  → 融合与去重
  → 重排序
  → 上下文组装
  → 生成
  → 引用校验/拒答
```

两条线通过稳定的 `chunk_id`、文档版本和权限元数据连接。离线管线更新了文档，在线索引必须能识别版本变化；在线请求找到了片段，也必须能追溯它来自哪份文档的哪一版。

## 2.2 一个 chunk 应该携带什么

只存一段文本是不够的。一个可维护的 chunk 记录至少要有：

```json
{
  "chunk_id": "refund-2026-c03-004",
  "doc_id": "policy-refund-2026",
  "version": "2026-07-01",
  "title": "年付套餐退款规则",
  "section": "3.2 促销年付",
  "page": 7,
  "text": "促销年付订单在首个计费周期内退款时，应扣除已使用的折扣金额……",
  "source_uri": "s3://kb/policy-refund-2026.pdf",
  "acl": ["support", "finance"],
  "content_hash": "sha256:...",
  "indexed_at": "2026-10-01T09:12:00Z"
}
```

这些字段各有用途：

- `chunk_id` 让引用、反馈和缓存有稳定坐标；
- `doc_id`/`version` 让旧索引可以替换而不是重复堆叠；
- `section`/`page` 让人能回到原文核对；
- `acl` 在检索前过滤权限，而不是生成后靠提示词保密；
- `content_hash` 用于增量索引，避免文本没变却重复计算 embedding。

教学系统常把这些字段全省掉，只留 `text`。原型能跑，但一旦要更新、引用、删除或做权限，就会发现自己没有足够的信息。

## 2.3 一次在线请求的预算

假设上下文窗口是 8,000 token，系统给一次回答分配如下预算：

| 部分 | 预算 | 说明 |
| --- | ---: | --- |
| 系统指令与输出格式 | 900 | 角色、拒答规则、引用格式 |
| 用户问题与会话摘要 | 600 | 当前问题和必要历史 |
| 证据片段 | 4,000 | 约 8—12 个短片段 |
| 输出预留 | 1,500 | 防止生成被截断 |
| 安全余量 | 1,000 | token 估算误差、工具返回 |

证据预算不是越大越好。窗口里塞入太多相似段落，会抬高成本，也可能让模型把注意力分散到互相矛盾的文本上。一个常见起点是：召回 30—80 个候选，重排后保留 5—12 个证据块，再根据问题类型调整。

这些数字是教学设计，不是通用最优值。代码、合同和表格需要更长的片段；客服问答可能需要更短、更精确的片段。

## 2.4 一条完整的教学轨迹

下面是一条虚构但结构完整的请求。假设用户问：

> 我们的年付专业版用了三个月，现在退款要扣多少？

### 第一步：查询改写

原始问题没有说明地区、订单类型和购买渠道。系统从会话状态中补全：

```text
standalone_query: 专业版年付订单使用三个月后退款金额
filters: {product: "pro", billing: "annual", region: "CN"}
```

如果会话中没有订单信息，系统不应该擅自补一个地区；它应该追问，或者明确给出地区假设。

### 第二步：并行召回

```text
vector_search(query, filter, k=40)
bm25_search(query, filter, k=40)
```

两路结果合并、按 `chunk_id` 去重，得到约 56 个候选。去重很重要：同一段文字可能出现在多个文档版本或多个镜像里。

### 第三步：融合与截断

用 RRF 或经过校准的分数合并两路结果，保留前 30 个进入重排。融合不是简单相加：BM25 和向量分数的尺度通常不同，直接相加会让某一路支配结果。

### 第四步：重排序

重排器逐条判断“这段文字是否真的能回答当前问题”，把“月付规则”“企业合同”“旧版本政策”排到后面。假设保留 8 条证据，每条不超过 500 token。

### 第五步：上下文组装

证据按“直接规则 → 例外 → 计算示例 → 旧版本说明”的顺序组织，并加上来源标签：

```text
[证据 1｜policy-refund-2026 §3.2｜2026-07-01]
促销年付订单在首个计费周期内退款时，应扣除已经使用的折扣金额……

[证据 2｜policy-refund-2026 §3.1｜2026-07-01]
年付订单的标准退款按未使用完整月份比例计算……
```

旧版本只能作为“历史差异”出现，不能被当成当前规则。来源标签要能让人回到原文，而不是只显示一个模糊的“知识库”。

### 第六步：生成与校验

模型输出答案、计算过程和引用。程序至少检查：

- 引用 ID 是否都来自本次提供的证据；
- 答案中的数字是否能从证据和订单数据推出；
- 是否遗漏了证据明确写出的例外；
- 如果没有足够证据，是否拒答或要求补充信息。

这一步不能保证语义完全正确，但可以挡住“引用了一个根本不存在的片段”这类明显错误。

## 2.5 常见断点

一条 RAG 链路可能在很多地方断掉：

| 断点 | 表面现象 | 首先检查 |
| --- | --- | --- |
| 文档解析 | 表格错位、页眉混入正文 | 解析器、页面结构、OCR |
| 切块 | 答案被切成两半 | chunk 边界、标题层级、overlap |
| 索引 | 新文档搜不到 | 增量任务、版本、索引刷新 |
| 查询 | 用户说“它”时检索错对象 | 会话改写、实体解析 |
| 召回 | 正确文档根本没进候选 | top_k、过滤条件、embedding |
| 重排 | 正确片段排到后面 | 重排模型、输入长度、标签偏差 |
| 组装 | 证据太多或顺序混乱 | 预算、去重、来源优先级 |
| 生成 | 有证据却答错 | 提示、冲突处理、模型能力 |
| 评测 | 看起来好，线上差 | 测试集分布、指标、人工抽检 |

排错时先确定断点，不要一上来就换 embedding 模型。一个切块错误，换再贵的向量模型也救不回来；一个权限过滤条件写错，重排器只会更精确地排出不该看的文档。

## 2.6 本章的结论

RAG 是一条有状态的管线：离线索引和在线请求通过稳定的片段标识、版本和权限连接。每一次请求都要经过查询改写、召回、融合、重排、组装和校验。

最重要的工程习惯是保留证据链：从答案能回到片段，从片段能回到文档版本，从文档版本能回到索引任务。没有这条链，系统只能“看起来能答”，无法定位和修正错误。
