# 第 10 章 生产系统与 Agentic RAG

## 10.1 从演示到生产

一个 RAG 演示可以在笔记本里读完几份 PDF，返回一段看起来不错的答案。生产系统要面对：

- 文档每天增删改，索引必须增量更新；
- 不同租户、角色和地区看到不同内容；
- 查询量、并发和延迟有上限；
- 失败要能定位、回滚和重试；
- 答案要能审计，引用要能回链；
- 成本要可预测。

生产化的第一步不是换更大的模型，而是把**数据生命周期**和**权限边界**固定下来。

## 10.2 索引管线

一个可维护的增量索引流程：

```text
扫描源系统
  → 计算文档 content_hash
  → 解析/切块
  → 生成 embedding
  → 写入新版本
  → 原子切换索引别名
  → 删除旧版本
```

关键设计：

- 每个文档有稳定 `doc_id` 和不可变 `version`；
- 解析、切块、embedding 都有版本号；
- 索引写入先进入临时版本，验证后再切换别名；
- 删除文档时同步删除向量、关键词索引和缓存；
- 失败任务可重试，不能留下半套索引。

不要在原地覆盖旧向量。一次失败的更新如果覆盖了可用版本，线上会突然查不到文档，且很难回滚。

## 10.3 权限和多租户

权限要在检索前执行：

```json
{
  "tenant_id": "t-42",
  "acl": ["support", "finance"],
  "region": "CN"
}
```

索引层应按租户或权限域分区，至少要让过滤条件参与候选选择。只在生成后检查“答案里有没有敏感词”太晚：无权文档已经进入上下文，可能影响答案，也可能被模型复述。

多租户系统还要防止：

- 缓存键缺少租户/权限，导致跨租户命中；
- 向量索引共享但过滤条件写错；
- 日志记录完整文档内容，造成二次泄露；
- 管理员账号被当作普通检索身份。

## 10.4 缓存与延迟

可以缓存的层次很多：

- embedding：相同文本和模型版本；
- 检索结果：相同查询、过滤、索引版本和权限；
- 重排分数：相同查询—候选对；
- 最终答案：只适合低风险、时效要求低的重复问题。

缓存键必须包含所有会改变结果的维度。对于政策、价格、库存等高频变化内容，设置短 TTL 或主动失效；不要把“昨天有人问过”当成今天仍正确的理由。

延迟优化通常先做：

1. 并行召回；
2. 减少候选数和无效重排；
3. 对长短文本分批；
4. 缓存高频查询；
5. 把非关键步骤异步化。

## 10.5 可观测性

每次请求至少记录：

- 查询原文和改写后的独立查询；
- 过滤条件；
- 每路召回的候选 ID 和分数；
- 重排后的证据 ID；
- 最终上下文 token；
- 答案、引用和拒答标记；
- 各阶段延迟和成本；
- 索引版本、模型版本、提示版本。

日志要脱敏。对失败样本保留足够信息复现，但不要把完整隐私文档长期写入普通日志。

## 10.6 Agentic RAG

传统 RAG 是固定管线：检索一次，生成一次。Agentic RAG 让模型决定：

- 是否需要检索；
- 检索哪个知识源；
- 是否需要改写查询；
- 读到的证据够不够；
- 是否再检索一次或调用其他工具。

这会带来更强的多跳能力，也带来新的风险：

- 循环检索，成本和延迟失控；
- 模型不断改写查询，偏离用户目标；
- 把检索结果中的恶意指令当成工具指令；
- 在证据不足时继续编造。

需要硬性限制：

```text
max_retrieval_rounds = 3
max_tool_calls = 6
max_context_tokens = 6000
stop_when_evidence_sufficient = true
```

“证据充分”不能只由模型说“够了”；可以用覆盖检查、引用检查和规则判断辅助。

## 10.7 安全边界

RAG 引入了新的攻击面：

- 文档中的提示注入；
- 恶意文档诱导模型调用工具或泄露数据；
- 通过查询注入探测其他租户内容；
- 引用链接指向钓鱼页面；
- 缓存或日志泄露敏感信息。

防御要分层：

1. 文档入库前做来源和权限标记；
2. 检索前过滤，检索后再次检查；
3. 证据作为数据展示，不自动升级为系统指令；
4. 工具调用走权限层，不因为“文档要求”就执行；
5. 输出做引用校验和敏感信息过滤；
6. 对高风险动作要求人工确认。

没有单一提示词能彻底解决提示注入。安全的重点是：即使模型被误导，也拿不到不该拿的权限、读不到不该读的数据、做不了不可逆的动作。

## 10.8 上线检查表

- 文档源、更新频率、删除策略是否明确？
- 解析失败、OCR 错误、表格损坏如何发现？
- 索引版本、embedding 版本、切块版本是否可追踪？
- 权限过滤在召回前是否生效？
- 重排和上下文预算是否满足延迟目标？
- 引用能否回到原文和版本？
- 无答案、权限不足、冲突证据是否能拒答或说明？
- 评测集是否覆盖长尾、多跳、对抗和高风险问题？
- 是否有回滚、降级和人工接管路径？

## 10.9 本章的结论

生产 RAG 的核心不是某一个模型，而是数据、权限、索引、上下文和评测共同构成的系统。

Agentic RAG 把“检索”从固定步骤变成可调用能力，扩大了系统边界，也放大了循环、权限和注入风险。越自主，越需要明确的预算、停止条件、证据检查和最小权限。

当系统能够在证据不足时说“不知道”，在文档冲突时说明差异，在权限不足时拒绝，并让每个结论回到可核对的来源，RAG 才真正从演示走向可用的知识系统。
