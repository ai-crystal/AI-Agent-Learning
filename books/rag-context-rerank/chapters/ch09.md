# 第 9 章 RAG 的评测

## 9.1 不要只测最终答案

一个 RAG 系统可能有四种不同的问题：

1. 正确文档没有被召回；
2. 正确文档被召回但排名太靠后；
3. 证据进了上下文，但模型没有正确使用；
4. 答案正确，但引用不到证据或引用了错误来源。

只测最终答案，会把前三种问题混成一个“答对了/答错了”的标签，无法知道该改哪一层。

评测至少要分层：

| 层 | 指标示例 | 回答的问题 |
| --- | --- | --- |
| 解析/切块 | 解析成功率、表格保留率 | 资料是否可读 |
| 召回 | Recall@k、MRR | 正确证据有没有出现 |
| 重排 | nDCG@k、Precision@k | 正确证据排得够不够前 |
| 生成 | 答案正确率、拒答率 | 回答是否正确 |
| 依据 | groundedness、引用精确率 | 答案是否被证据支持 |
| 系统 | 延迟、成本、错误率 | 是否能稳定运行 |

## 9.2 Recall@k 和 nDCG

**Recall@k**：前 k 个结果里是否包含至少一个相关文档（或所有必要文档）。它适合衡量“有没有找到”。

假设某题需要两份证据 E1、E2，前 5 个结果只包含 E1，那么：

```text
Recall@5（至少一个相关）= 1
Recall@5（全部相关）   = 0.5
```

团队必须明确自己用的是哪一种，否则同一个数字会被解释成不同意思。

**nDCG@k** 考虑相关性和位置。高相关文档排在第一，比排在第五贡献更大。它适合比较不同重排策略，但需要相关性等级（例如 0/1/2），不能只用“是否相关”一个标签。

这些指标需要人工或可靠标注。用模型自动标注时，要抽检标注一致性，并保留原始证据和判断理由。

## 9.3 答案正确不等于有依据

一个问题可能有三类答案：

- **正确且有依据**：答案与事实一致，引用支持结论；
- **正确但无依据**：答案碰巧对，但证据没有支持它，换一份资料就可能错；
- **流畅但错误**：语言自然，结论错误，引用看似相关。

RAG 评测必须把“答案正确”和“答案被证据支持”分开。一个常用的检查是：

```json
{
  "answer_correct": true,
  "grounded": false,
  "citation_precision": 0.5,
  "reason": "金额正确，但引用的片段只说明了退款条件，没有给出计算公式。"
}
```

这类样本对改进系统很有价值：它说明问题不在知识，而在上下文或生成。

## 9.4 构造测试集

测试集应覆盖：

- 常见问题：来自真实日志，代表主要分布；
- 长尾实体：产品编号、地区、合同类型；
- 否定和例外：不适用、除外、需要审批；
- 多跳问题：需要两份以上文档；
- 无答案问题：知识库没有答案，系统应拒答；
- 权限问题：用户无权查看的文档不能出现在答案或引用中；
- 对抗问题：文档中包含提示注入或误导内容。

不要只用自己写的、看过答案的问题。真实用户会省略条件、用错术语、问不存在的东西。测试集要包含这些“不整洁”的输入。

## 9.5 一个评测用例

```json
{
  "case_id": "refund-annual-discount-001",
  "question": "年付专业版用了三个月，含首年折扣，退款要扣多少？",
  "filters": {"product": "pro", "billing": "annual", "region": "CN"},
  "gold_evidence": ["policy-refund-2026#3.1", "policy-refund-2026#3.2"],
  "expected_points": [
    "按未使用完整月份比例计算",
    "扣除已使用月份的折扣差额",
    "说明最终金额依赖订单实际支付与折扣"
  ],
  "forbidden": ["直接套用月付规则", "承诺固定退款金额"],
  "difficulty": "multi-condition"
}
```

评分可以分三层：

1. 证据层：gold evidence 是否进入前 k；
2. 答案层：是否覆盖 expected points，是否出现 forbidden；
3. 依据层：引用是否支持每个关键结论。

评分器要能解释失败原因，而不只是给 0/1。否则团队无法知道是切块、检索、重排还是生成出了问题。

## 9.6 评测的陷阱

**测试集污染。** 测试问题或答案进入训练/提示示例，分数虚高。训练、开发、测试要分开。

**只测平均分。** 平均分掩盖了高风险类别；金额、权限、拒答应单独统计。

**用同一个模型当出题人和裁判。** 它会偏好自己的表达和盲区。需要人工抽检、规则检查和不同模型交叉验证。

**忽略延迟和成本。** 一个准确率高 2 个点、延迟翻倍的系统，未必适合在线客服。

**忽略拒答。** 只在有答案的问题上评测，会奖励“硬答”；必须加入无答案和权限不足样本。

## 9.7 回归与上线

每次修改切块、embedding、索引、重排或提示，都应该跑同一套回归集，并记录：

- 指标变化；
- 失败类型变化；
- 平均/峰值 token 和延迟；
- 受影响的文档类别；
- 是否引入新的权限或引用错误。

上线后继续收集真实问题，脱敏后加入测试集，但不要把线上答案直接当成标准答案。人工确认、用户反馈和可验证的业务结果，才是高质量标签的来源。

## 9.8 本章的结论

RAG 评测要定位链路，而不是只给最终答案打分。Recall@k 看有没有找到，nDCG/Precision 看排得好不好，groundedness 和引用精确率看答案有没有依据，延迟和成本看能不能上线。

一个成熟的评测集应覆盖常见、长尾、多跳、无答案、权限和对抗输入。没有这些分层，团队很容易把“模型答得流畅”误当成“系统可靠”。
