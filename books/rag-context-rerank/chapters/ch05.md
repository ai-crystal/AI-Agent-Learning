# 第 5 章 混合检索与查询改写

## 5.1 为什么向量不够

向量检索擅长“意思相近”，但很多企业查询有精确约束：

- 订单号 `A1023`；
- 版本 `v2.4.1`；
- 条款编号 `§3.2`；
- 产品名、客户名、地区代码；
- 明确否定：“不含安装服务”。

这些 token 在 embedding 中可能被平滑掉。BM25 这类词法检索依赖词频、逆文档频率和长度归一化，对精确词、稀有词和编号更敏感。它不理解同义词，但能找回向量模型漏掉的字符串。

混合检索的基本判断是：**两者都可能对，但不能假设它们的分数可以直接相加。**

## 5.2 BM25 的直觉

BM25 给一个查询词和文档打分，核心因素包括：

- 查询词在文档中出现得越多，分数通常越高，但收益递减；
- 词越稀有，区分度越高；
- 文档越长，出现同样次数的词应该被折损；
- 不同查询词的分值累加。

以教学查询 `年付 退款 折扣` 为例，文档 A 同时出现三个词，文档 B 只出现“退款”。BM25 会给 A 更高分；但它不会知道“折扣”是否真的适用于“年付”，这需要后面的重排。

中文 BM25 还涉及分词：按字、按词或按业务词典切分，结果完全不同。要把产品名、型号、地区名加入词典，否则“A1023”可能被拆成无意义的片段。

## 5.3 倒数排名融合

当向量检索返回一个名次列表、BM25 返回另一个名次列表，可以用 Reciprocal Rank Fusion（RRF）合并：

```text
score(d) = Σ_i 1 / (k + rank_i(d))
```

其中 `rank_i(d)` 是文档 d 在第 i 路结果中的名次，`k` 是平滑常数（常见起点 60，但不是定律）。RRF 只看名次，不看原始分数，因此避免了两路分数量纲不同的问题。

教学示例：

| 文档 | 向量名次 | BM25 名次 | RRF 近似分 |
| --- | ---: | ---: | ---: |
| c03 促销年付例外 | 1 | 4 | 1/61 + 1/64 ≈ 0.0320 |
| c02 年付标准规则 | 2 | 2 | 1/62 + 1/62 ≈ 0.0323 |
| c01 月付规则 | 3 | 8 | 1/63 + 1/68 ≈ 0.0306 |

在这个虚构例子里，c02 因为两路都靠前而略胜；c03 虽然向量第一，但 BM25 第四。RRF 不是要选出“绝对正确”的文档，而是让多路证据共同决定候选顺序。

如果确实要融合原始分数，必须先做校准或训练一个融合器，并分别验证每一路的贡献。不要直接把余弦相似度和 BM25 分数相加。

## 5.4 查询改写

用户的问题经常不适合直接检索：

- 指代：“那它还能退吗？”——它是什么？
- 省略：“中国区呢？”——承接上一轮的产品和订单类型；
- 口语：“买了三个月不想用了”——对应“使用三个月”“退款”；
- 多意图：“退款规则和发票怎么开”——需要拆成两个子查询；
- 过度具体：“A1023 订单在 2026-07-01 之后……”——可能应直接走结构化查询。

查询改写可以生成一个独立的 `standalone_query`，并抽取过滤条件：

```json
{
  "original": "那它还能退吗？",
  "standalone": "专业版年付订单使用三个月后退款规则",
  "filters": {"product": "pro", "billing": "annual", "region": "CN"},
  "subqueries": []
}
```

改写必须保守。会话中没有地区时，不要凭空补“CN”；没有订单类型时，不要把“年付”当成事实。错误的改写比不改写更糟，因为它会把检索引向一个看似确定、实际错误的方向。

## 5.5 多查询与分解

对复杂问题，可以生成 2—4 个互补查询：

```text
原问题：年付专业版用了三个月，退款要扣多少？
q1: 年付专业版退款计算规则
q2: 促销年付退款折扣扣除
q3: 退款申请时间和条件
```

分别召回后合并去重，再统一重排。查询越多，召回覆盖率可能越高，但成本和重复候选也上升。要限制子查询数量，并记录每个候选来自哪个查询，便于评测。

分解适合多跳问题，例如“某政策的例外条款是否适用于我所在的地区”。第一跳找政策主体，第二跳找地区例外；不要期待一个向量查询同时命中两跳的所有证据。

## 5.6 过滤条件从哪来

过滤条件最好来自结构化系统，而不是模型猜：

- 订单服务提供产品、地区、购买时间；
- 身份系统提供租户和权限；
- 文档索引提供生效日期、文档类型和语言；
- 会话状态提供已经确认的实体。

模型可以从自然语言中抽取候选条件，但高风险条件（地区、权限、合同类型）应由程序校验。一个错误的 `region` 过滤会让正确文档根本进不了候选集，而后面的重排再强也无法补救。

## 5.7 失败模式与评测

**同义词漏召回。** 用户说“退费”，文档写“退款”；需要同义词扩展或向量检索补足。

**编号被分词破坏。** 需要业务词典、字符级检索或结构化字段。

**改写过度。** 模型把“可能”改成“确定”，把“欧洲”改成“德国”；需要保留原问题并让改写可审计。

**多路结果重复。** 同一文档多个块进入候选，挤占名额；需要按文档去重或限制每篇文档的候选数。

**过滤条件过严。** 正确文档因一个可选字段缺失被排除；需要区分“未知”与“不匹配”。

评测时分别看：

- 每一路单独的 Recall@k；
- 融合后的 Recall@k；
- 查询改写的正确率；
- 过滤条件导致的漏召回；
- 总候选数和下游重排成本。

不要只比较“混合检索的最终答案”。如果最终答案没变，可能只是两路都在犯同一个错误。

## 5.8 本章的结论

混合检索用词法补语义，用语义补同义词；查询改写把会话中的隐含条件变成可检索的独立问题。两者都必须保守、可审计，并且把权限和业务过滤放在召回阶段。

一个常见的顺序是：先做实体和条件解析，再生成独立查询，并行召回，RRF 融合，按文档去重，最后交给重排。这个顺序不是唯一答案，但每一层都要能被单独测量。
