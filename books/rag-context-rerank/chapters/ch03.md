# 第 3 章 文档解析与切块

## 3.1 先别急着切

RAG 的上游不是“文本文件”，而是各种结构：PDF 有栏、页眉页脚、表格和扫描页；HTML 有导航、广告和正文；Markdown 有标题层级；数据库有字段；工单有状态和权限。

解析阶段的目标不是把所有内容变成一样长的一串字，而是保留三类信息：

1. **语义边界**：标题、段落、列表、表格行；
2. **来源坐标**：文档、版本、页码、章节、URL；
3. **使用约束**：权限、生效日期、语言、地区、客户范围。

如果解析时把页眉“内部资料·请勿外传”拼进每段正文，检索会把页眉当语义内容；如果表格的行列关系丢了，模型看到的就是一串无法对应的数字。切块不能修复上游的结构损失。

一个解析后的中间记录可以写成：

```json
{
  "doc_id": "policy-refund-2026",
  "section": "3.2 促销年付",
  "page": 7,
  "text": "促销年付订单在首个计费周期内退款时，应扣除已经使用的折扣金额。",
  "source_uri": "s3://kb/policy-refund-2026.pdf",
  "effective_from": "2026-07-01",
  "acl": ["support", "finance"]
}
```

## 3.2 四种切块方式

**固定长度切块**：每 N 个 token 切一刀，可以留少量重叠。实现简单，边界稳定，但可能把一个条件句和它的例外切开。适合作为基线，不适合作为最终方案。

**按结构切块**：优先在标题、段落、列表项、表格行等自然边界切分，再对过长的单元二次切分。它保留了章节关系，通常比固定长度更可解释。

**递归切块**：先尝试大边界（章、节），超过长度再降到段落、句子；仍然超长才按 token 切。它的实际行为取决于分隔符顺序和长度参数，必须用真实文档检查。

**父子块**：子块用于精确检索，父块用于给模型提供更完整的上下文。检索命中子块后，把它的父块或相邻块取出来。它解决“短块检索准、长块上下文足”的矛盾，但会增加存储和组装复杂度。

不存在通用的 `chunk_size=512, overlap=50`。对客服问答，短块可能更精确；对合同条款，切掉条件会致命；对代码，函数和类边界比固定 token 更重要。

## 3.3 一个切块实例

假设原文是：

> 年付专业版在购买后 30 天内可以申请全额退款。超过 30 天后，按未使用完整月份比例退款；但如果订单使用了首年折扣，退款金额需要先扣除已使用月份的折扣差额。企业合同不适用本节。

如果按 50 token 硬切，可能得到：

```text
块 A：年付专业版在购买后 30 天内可以申请全额退款。超过 30 天后，按未使用完整月份比例退款；
块 B：但如果订单使用了首年折扣，退款金额需要先扣除已使用月份的折扣差额。企业合同不适用本节。
```

用户问“超过 30 天且有首年折扣能退多少”，只用块 A 会漏掉折扣扣除，只用块 B 会缺少“按未使用月份比例”的主规则。更好的切法是让主规则和例外处在同一块，或者通过父子块把两块一起取回。

```text
chunk_id: refund-2026-3.2-01
section: 3.2 促销年付
text: 年付专业版……（主规则 + 折扣例外，约 180 token）
parent_id: refund-2026-3
```

注意：为了让例子完整，这一块比通用问答块更长。**块长度应服务于语义完整性，而不是追求统一数字。**

## 3.4 元数据决定检索质量

同样是“退款”两个字，可能来自：

- 当前有效政策；
- 两年前的旧政策；
- 某个地区的特殊规定；
- 内部培训材料；
- 客户工单中的个人经验。

如果这些片段没有 `effective_from`、`region`、`doc_type` 和 `acl`，向量检索只能凭语义相似度混在一起。查询改写可以把“中国区年付”变成过滤条件，但前提是索引里有这些字段。

建议至少保留：

| 字段 | 用途 |
| --- | --- |
| `doc_id`, `version` | 去重、回滚、引用 |
| `section`, `page` | 人工核对 |
| `effective_from/to` | 过滤过期政策 |
| `region`, `product` | 业务过滤 |
| `acl` | 检索前权限 |
| `content_hash` | 增量索引 |

## 3.5 解析与切块的失败模式

**表格被拆散。** 行头和列头分离后，数字失去含义。解决方式是按表格整体切块，或把每一行转成“列名: 值”的结构化文本。

**否定和条件被截断。** “除以下情况外”“不适用于”被切到下一块，检索到的片段会表达相反意思。解决方式是提高边界优先级、保留相邻块，或在组装时取父子块。

**页眉页脚重复。** 每页都有的公司名、密级、页码会污染语义。解析时删除重复模板，或将其放入单独元数据。

**OCR 错字。** 数字、专有名词和否定词最容易错。需要抽检、词典校正和原文回链；不要假设 OCR 文本一定可信。

**文档版本重叠。** 新旧政策同时进入索引，检索会给出冲突证据。必须用版本和生效日期过滤，并让旧版本只作为历史对照。

## 3.6 怎样验证切块

不要用“看起来不错”判断切块。准备一组带标准答案的问题，测量：

- 正确证据是否出现在前 k 个块中（Recall@k）；
- 正确证据是否被切成了多个不完整块；
- 加入相邻块或父块后，答案是否恢复；
- 块长度分布是否极端：过短导致语义不全，过长挤占上下文；
- 解析失败率、表格保留率和 OCR 抽检错误率。

切块是一个需要评测的上游模型，不是一个一次性参数。每次换解析器、文档模板或业务政策，都应该重新看这些指标。

## 3.7 本章的结论

解析保留结构，切块保留语义，元数据保留来源和约束。三者缺一不可。

一个块应该能独立表达一个可回答的意思，同时知道自己来自哪里、何时有效、谁能看。做不到这三点，后面的向量、重排和上下文组装都只能建立在不可靠的输入上。
