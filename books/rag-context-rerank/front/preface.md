# 前言

当模型不知道某个事实，或者参数里的知识已经过时、不完整，系统需要的不是再写一句提示，而是找到外部证据、判断相关性、把证据组织进上下文，并对答案负责。**模型不知道的东西，系统怎样让它知道。**

大模型有两个看起来相似、实际不同的问题。第一，参数里没有某个事实；第二，参数里有事实，但已经过时、不完整，或者没有权限使用。前者可能需要更新知识来源，后者可能需要重新检索，或者在回答时明确说明限制。把文档全部塞进提示词不是答案：窗口有限，证据会互相冲突，检索会漏召回，模型还会把无关片段当成依据。

本书把 RAG（Retrieval-Augmented Generation，检索增强生成）当作一条工程链路，而不是一个单点技术。一次请求至少要经过：

1. 解析文档并切成语义单元；
2. 为查询和文档建立可检索的表示；
3. 从大量候选中召回一批可能相关的片段；
4. 用更贵的模型或规则重排候选；
5. 在 token 预算内组装证据、指令和问题；
6. 生成带依据的答案；
7. 评测检索、排序、答案和引用的质量。

重排序不是链路的装饰，它解决的是“召回阶段宁多勿漏，生成阶段宁准勿杂”之间的矛盾。上下文管理也不是把所有历史越留越多，它要在证据、指令、历史、工具返回和输出预算之间分配空间。

## 适合谁

- 已经能写基本 Python 或调用模型 API，但还没有做过完整 RAG 系统的读者；
- 做过“向量库 + 提示词”原型，发现答案经常无依据、漏资料或引用错误的读者；
- 想理解检索、重排序、上下文预算和评测之间的取舍，而不是只记某个框架 API 的读者。

书里会用到 JSON、HTTP、SQL 和少量 Python 伪代码。没有这些基础也可以先读机制部分，把代码当作结构化示例。

## 阅读路径

- **先建立整体图景**：第 1—2 章。
- **检索效果不好**：第 3—6 章，尤其切块和重排序。
- **答案没有依据或上下文太乱**：第 7—8 章。
- **需要上线和回归**：第 9—10 章。

## 一个约定

书里的公司、文档、查询和分数都是教学示例，除非明确标注，不代表某个产品、论文或真实客户的数据。工程参数（`top_k`、chunk size、预算）也都是起点，不是通用最优值。每一章最后都会指出应该怎样用自己的数据验证，而不是把示例数字照搬上线。
